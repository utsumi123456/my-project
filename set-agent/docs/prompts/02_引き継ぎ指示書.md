# Set Agent — セッション引き継ぎの指示書（チーム共有用）

Claude Code のセッションは、文脈が長くなると要約されたり、処理負荷で終了したりします。
Set Agent では **`HANDOFF.md` 1 ファイルを引き継ぎの正本**にして、次のセッション（別の日、別の人、
別のアカウント）が「ここだけ読めば続きから拾える」状態を保っています。この文書は、その運用ルールと、
実際に使った引き継ぎプロンプトです。

---

## 1. 引き継ぎの基本形

### 受け取る側（新しいセッションの最初の 1 行）

```
@"C:\Users\<you>\source\my-project\set-agent\HANDOFF.md"
```

これだけです。Claude は HANDOFF の先頭セクション「▶ 次のセッションはここから」を読み、
「次にやること」の着手可能な項目を選び、着手前に一言（何をするか）を返してから作業に入ります。

### 渡す側（セッションを終える前に Claude に頼むこと）

```
HANDOFF を更新して push して。次のセッションがここだけ読めば続きから拾える形で。
```

Claude は「▶ 次のセッションはここから」を書き換え、日付つきの追記セクションを 1 つ足し、
コミットして push します（2026-09-16 の例: `cfd2f23 HANDOFF: start-here summary for the next session`）。

## 2. `HANDOFF.md` の構造（この順で並ぶ）

```
# Set Agent — 引き継ぎメモ

## ▶ 次のセッションはここから（YYYY-MM-DD HH:MM 時点の引き継ぎ）   ← 常に最新。ここだけ読めばよい
### いま何ができているか（実機で全部確認済み）
### 最新の状態            ← main のコミット、exe のビルド時刻、テスト件数、probe の結果
### 配布                   ← リンク、CI、未検証の環境
### 次にやること（ユーザー決定、日時。上から順）  ← 済んだ項目は ~~取り消し線~~ + 「済み（日時）」
### 動かし方と判定          ← コマンドと、その判定基準
### 主要ファイル            ← 何がどこにあるか（表）
### 地雷                   ← 踏むと時間を溶かす罠。原因と回避を 1 行ずつ

---

## YYYY-MM-DD 追記（時間帯）— 何をしたか   ← 新しいものが上。作業ログの正本
...（過去の追記が日付順に続く）

## 1〜8. 恒久セクション（これは何か／置き場所／できていること／設計上の約束／UI の判断基準）
```

### 各セクションに書くもの・書かないもの

| セクション | 書く | 書かない |
|---|---|---|
| いま何ができているか | 実機で確認済みの機能だけ。画面の並び順どおり | 予定・希望 |
| 最新の状態 | `main` のハッシュ、exe の時刻と一致するソース、テスト件数、probe の PASS/FAIL、gh のログイン状態 | 途中の作業ツリー |
| 次にやること | **ユーザーが決めた**順番と日時。Claude の提案は「候補」と明記 | Claude が勝手に決めた優先順 |
| 動かし方と判定 | コマンドと「何が出れば OK か」 | 説明だけのコマンド |
| 地雷 | 現象 → 原因 → 回避。1 件 1〜3 行 | 一般論 |
| 日付つき追記 | やったこと・判断とその理由・実測値・未検証のこと | 感想 |

### 書き方のルール

- **状態と規約だけを持つ。仕様の正典は別ファイル**（`rekordbox_set_agent_spec.md`）。HANDOFF は作業状態。
- **数字を残す**（137:18、48 曲、7.1 秒、96/96）。次のセッションが回帰を見分ける材料になる。
- **ユーザー決定は日時つきで**（「ユーザー決定、2026-09-16 22:17」）。あとで「誰がいつ決めたか」が分かる。
- **未検証は未検証と書く**（「macOS 版は実機未検証」「LLM 実キーは未疎通」）。できたように書かない。
- **済んだ項目は消さず取り消し線**にして「済み（日時）」を付ける。何が終わったかが履歴として残る。
- **前セッションの口調・判断を否定しない。** 事実（何が動くか）と判断（なぜそうしたか）を分けて書く。
- **口調は です・ます**（ユーザー指示、2026-09-16）。前任アカウントの命令形は全面置換した。

## 3. 引き継ぎで実際に効いたこと（2026-09-16 → 09-17 の実例）

- **前セッションは処理負荷のため強制終了**した。それでも 09-17 の最初の 1 行（`@HANDOFF.md`）だけで、
  Claude は「次にやること 3・4」を選んで実装・検証・push・exe ビルドまで進めた。
- **「動かし方と判定」があったので、新セッションは probe を最初に回して回帰の有無を確認できた。**
- **地雷の記録が時間を節約した**例:
  - 「probe とテストを並走させない（復号キャッシュが固定パス）」→ 新セッションは最初から直列で回した。
  - 「長い置換スクリプトはファイルに書いて `python <path>`」→ ENAMETOOLONG を踏まずに済んだ。
  - 「GUI exe から子プロセスを起こすときは `CREATE_NO_WINDOW`」→ Claude Code 子プロセスでも最初から付けた。
- **「次にやること」にユーザーの決定日時があったので、Claude は順序を勝手に変えなかった**
  （1 は「後日」、2 は LLM キーが要る、と読み、3・4 から着手し、その判断を最初のメッセージで説明した）。

## 4. 自動メモリとの役割分担

Claude Code には自動メモリ（`~/.claude/projects/<project>/memory/`）もあります。役割は分けています。

| 置き場 | 何を書く | 誰が読む |
|---|---|---|
| `HANDOFF.md`（リポジトリ内） | プロジェクトの状態・決定・地雷。**チームで共有**する | 誰のアカウントでも、次のセッションの Claude |
| 自動メモリ（ユーザー個人） | **この PC 固有**の作業上の癖（ファイルが CRLF、Git Bash が `/PID` をパスに変える、ヒアドキュメントの長さ制限） | 同じアカウントの Claude だけ |

リポジトリに入れて困らないことは HANDOFF へ。個人の環境の話はメモリへ。

## 5. 引き継ぎ時に Claude へ頼む定型文（コピー用）

セッションを終えるとき:
```
ここまでを HANDOFF に反映して push して。
「▶ 次のセッションはここから」を今の状態に書き換え、今日の追記セクションを足す。
次にやることは私が決めた順番のまま。未検証のものは未検証と書く。
```

別の人に渡すとき（相手が別 PC・別アカウント）:
```
HANDOFF の「動かし方と判定」と docs/DISTRIBUTION.md を読んで、この PC で
python -m unittest discover -s tests -q と python -m tools.probe_compat を回し、
結果を HANDOFF の「最新の状態」に追記して。差分があれば直す前に報告して。
```

状態が分からなくなったとき:
```
HANDOFF の「最新の状態」と git log の先頭 5 件、テストと probe_views の結果を突き合わせて、
ずれているところを列挙して。直すのはその後。
```

## 6. 従った・参考にしたスキル

引き継ぎファイルの運用そのものは Set Agent 固有の慣習で、特定のスキルの手順ではありません。
考え方として参考にしたもの:

| スキル | 取り入れた点 |
|---|---|
| `superpowers:writing-plans` | 「次にやること」を実行可能な粒度で、判定基準つきで書く |
| `superpowers:verification-before-completion` | 引き継ぎ前に probe とテストを回し、実測値を「最新の状態」に残す |
| `superpowers:finishing-a-development-branch` | 区切りごとにコミット・push し、HANDOFF の更新を最後のコミットにする |
| `anthropic-skills:consolidate-memory`（考え方） | 状態の正本を 1 か所にまとめ、重複を作らない。個人の環境の話はメモリ側へ |
| `gsd:pause-work` / `gsd:resume-work`（考え方） | 「中断しても次が続きから拾える」ための状態ファイルという発想。GSD のワークフロー自体は使っていない |
