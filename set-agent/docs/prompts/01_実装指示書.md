# Set Agent — Claude への実装指示書（チーム共有用）

Set Agent（rekordbox のセット尺・展開を設計する常駐パネル）を Claude Code で作ったときに、
実際に Claude へ渡した指示と、その背後にある約束をまとめたものです。同じやり方で別のプロトを
作るとき、あるいは Set Agent を引き続き育てるときに、このまま貼って使えます。

構成:
1. セッションの始め方（毎回同じ 1 行）
2. 実際に使ったプロンプト原文（2026-09-17 の 1 日分）

## 1. セッションの始め方

Claude Code（デスクトップ版の Code タブ、作業ディレクトリ `my-project/set-agent`）を開いて、
最初のメッセージはこれだけです。

```
@"C:\Users\<you>\source\my-project\set-agent\HANDOFF.md"
```

`HANDOFF.md` の先頭「▶ 次のセッションはここから」に、現在の状態・次にやること・動かし方・地雷が
書いてあります。Claude はそれを読んで「次にやること」の着手可能な項目から始めます。
（引き継ぎファイルの書き方は `02_引き継ぎ指示書.md`。）

## 2. 実際に使ったプロンプト原文

短い指示で回るのは、規約が HANDOFF に蓄積されているからです。以下は 2026-09-17 の 1 日で
Claude に送った全プロンプトです（順番どおり）。

### 2-1. 続きの着手

```
@"…\set-agent\HANDOFF.md"

### 2-2. 方式検討を先に、実装は後に（AI エージェントの接続方式）

```
AIエージェントを実装するにあたってAPI以外の方法がないかを検討したい。
実現方法が確立したのち、実装を行う。
→API方式では、エンタープライズ契約アカウントの場合、管理者による制限で取得できず、
  このPC及びほかのPC環境でAPIを取得できない可能性あり
→したがって、以下に要求する仕様を記載した

AIエージェント実装においての要求
必須
・AIエージェントをset agentの一機能として使用できること
・解析データを基に現段階で実装予定の機能を実現できること
・他のPC環境（claudeエンタープライズ契約アカウント）でもAIエージェント機能を確実に導入できること
理想（優先順）
0.実装、検証がclaudeが行うアクションで完結する。
1.ユーザー側が能動的アクションをせず、簡単にAIエージェントを各PC環境で導入できること
2.AIエージェントの応答速度が実用的範囲で収まること（1秒～30秒）
3.AIエージェントのが高度な出力を行うこと（モデルの違い）
```

→ Claude は候補 6 方式を実測つきで比較し（`docs/llm_backend_2026-09-17.md`）、採用案を提示。
ユーザーが「進める」と答えてから実装した。**「検討 → 確立 → 実装」と段階を切り、必須と理想を
優先順つきで書いた**のがこのプロンプトの要点。

### 2-4. 使ってみてのフィードバック（仕様変更）

```
set bpmに関してのフィードバック
・DJプレイの前提として、プレイリスト楽曲のBPMをすべて原曲のままプレイするのはごく稀である。
  （プレイリスト内の楽曲BPMが統一されていた場合を除く）

  BPM140として予測時間を算出。（BPM160の場合は～以下同様）
→BPM変化ありの項目は、BPMがいくつの値からいくつの値に変化するかが不明瞭なため
  BPM○○→BPM△△といった表示にする。（最初の変化点は＜Set BPMで設定した値＞→
  ＜ユーザーが入力するBPM＞といった表記にする）

energyグラフを表示する詳細＞全体タブについて
現在、全体のタブと詳細タブでどちらもスクロール操作が要求されている。
全体タブのグラフについて、グラフを近似することで以下の点を満たしたものにしたい
・縦長表示にした際に、横方向に圧縮され、山谷の視認性が低下するのを防止する
・スクロールが必要ないようにする。（全体を描写）
・やはり想定する仕様環境はrekordboxのサブウィンドウとして使用するため、縦長画面での使用が主である

## 3. プロンプトの書き方で効いたこと

- **HANDOFF を唯一の入口にする。** 毎回の指示は短くてよい。文脈・規約・地雷はファイル側に蓄積する。
- **決めてほしいことは「決めて」と言う。** 「短い Mix の項目の意味が分からない、削除か改名か決めて」の
  ように委ねると、Claude は判断と理由を残して進む。
- **必須と理想を分け、理想に優先順を付ける。** 方式比較の表がそのまま出てくる。
- **DJ の前提を先に書く。** 「原曲 BPM のままかけることは稀」という一文で、既定値の設計が変わる。
- **段階を切る。** 「検討 → 実現方法が確立したのち実装」と書けば、Claude は途中で止まって確認する。
- **フィードバックは実際に触った感想でよい。** 数値や実装方法は Claude が測って決める。
- **できないことは断ってもらう。** rekordbox の更新や Mac 実機のように環境が要るものは、
  「準備だけして手順を残す」形に Claude が変えてくる。

## 4. Claude に守らせている設計上の約束（`HANDOFF.md` §7・§8 から）

これらは HANDOFF に常駐しているので、毎回のプロンプトには書きません。

- **数値は必ず解析エンジン（`analysis.*`）から取る。LLM に暗算させない。** UI も例外ではない。
  評価ハーネスは「回答中の mm:ss がすべてツール結果に由来するか」を機械的に判定する。
- **変更は必ず Command 経由で History に積む。** 手編集もエージェント提案も同じ道（undo できる）。
- **エージェントは Draft を直接いじれない。Change Set を出すだけ。** 適用はユーザーがチェックして決める。
- **候補曲は実在曲だけ。曲名を作らない。**
- **フレーズ解析が無い曲は「データなし」と明示し、中間値で埋めない。**
- **LLM が落ちても壊れない。** 接続できなければルールベースの Advisor に落ち、そう表示する。
- **rekordbox には書かない（read-only）。** master.db と -wal を読むだけ。
- **他人の PC で最初の 1 回が全て。** 見つからない・読めないときは理由と次の手を出す。
- **文言は です・ます。** 命令形・断定調にしない。
- **新しい画面を足すときは Tier 1（常時）/ 2（要求したら）/ 3（ホバー）のどこに入るか先に決める。**
- **タイポは 4 段階、文字色は 3 段階、フォントは rekordbox と同じ Arial 系。色相は rekordbox に合わせる。**

## 5. 検証と完了の基準（Claude が「できた」と言う前に通すもの）

```
python -m unittest discover -s tests -q          # 単体テスト（2026-09-17 時点 199 件）
python -m tools.probe_views acid 460 940         # UI の実測（WebView2 の DOM から数値を読む。スクショは使わない）
python -m tools.probe_polish acid 400 900        # 文字サイズ・コントラスト・フォーカスの下限
python -m tools.probe_agent acid                 # ドロワー → 提案 → 適用 → undo
python -m tools.eval_agent acid                  # 実 Claude で 6 シナリオを自動判定（数値の出所・目標到達・時間）
python -m tools.probe_compat                     # rekordbox 互換性（復号・列・単位・PSSI・アートワーク）
python build.py                                  # テスト → exe → dist/
git push origin main                             # 区切りごとに push。タグ v* で Release
```

- probe と単体テストは並走させない（復号キャッシュが固定パス）。
- 完了報告には実測値を添える（何秒・何件・何 px）。感想ではなく数字。
- できなかったこと・確認できなかったことは、報告の最初に書く。

## 6. 従った・参考にしたスキル

Claude Code に入っている「スキル」（手順書）のうち、この実装に関わったものです。
呼び出したものと、考え方だけ取り入れたものを分けています。

### 実際に呼び出したもの（前セッション、UI の磨き込みパス 2026-09-16）
| スキル | 何に使ったか |
|---|---|
| `frontend-design` | 磨き込みの方針決めと自己批評（情報・配置は変えず、間隔・階層・タイポ・色だけ整える） |
| `baseline-ui` | 守るべき下限（最小文字 11px、コントラスト 4.5:1、フォーカス可視）。`probe_polish` の判定軸になった |
| `design-review` | レビューの観点（読む順番、重複、意味の分からない項目） |

### 考え方を取り入れたもの（2026-09-17 のセッション。Skill としての呼び出しはしていない）
| スキル | 取り入れた点 |
|---|---|
| `superpowers:brainstorming` | 実装前に方式を比較し、採用案をユーザーに確認してから作る（§2-2） |
| `superpowers:writing-plans` | 設計メモ（`docs/llm_backend_2026-09-17.md`）を先に書き、要求との対応表を残す |
| `superpowers:test-driven-development` | `claude` CLI を偽装するスタブで単体テストを固定してから実装を進めた |
| `superpowers:systematic-debugging` | 評価で FAIL が出たら、原因（記録漏れ／ツール出力の切り詰め／スキーマ）を特定してから直す |
| `superpowers:verification-before-completion` | 「できた」と言う前に probe と eval を回し、実測値で報告する |
| `dataviz` | ENERGY 曲線の近似（3px バケット平均）と、解析なし区間を補間しない方針 |
| `claude-api` | Claude Code CLI の headless モードと MCP ツール定義の作法 |

### ユーザー側の設定として効いていたもの
- `~/.claude/CLAUDE.md`（グローバル指示）: 「ユーザーが問題を報告したら調査してから直す」「変更後に検証」
  「複数の独立作業は並列に」などの決定ルール。
- 自動メモリ（`~/.claude/projects/<project>/memory/`）: 「長い置換スクリプトはファイルに書いて実行する」
  「ファイルは CRLF」など、この PC 固有の地雷。
